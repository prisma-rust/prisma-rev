# 类蔚蓝银河恶魔城：功能完整拆解与引擎需求映射

Nov 9, 2026 · @Jason Gu

## 1. 项目定位与设计支柱

这是一个约 3–4 小时流程的 2D 像素银河恶魔城：移动手感对标《蔚蓝》，世界结构对标银河恶魔城（能力即钥匙、回溯探索）。它的首要目的不是成为爆款，而是用一组真实、互相牵连的需求把你的引擎逼到“够用”。

**一句话定义（暂定名《回声之井》）**：玩家沿着一口废弃的垂直巨井向下探索，每获得一种移动能力，就能进入此前够不到的房间，最终抵达井底并面对最终 Boss。

**四条设计支柱**

1. **手感第一**：移动精确、宽容、可预测。所有“让人觉得公平”的细节（土狼时间、输入缓冲、角落修正）都是硬需求，不是润色。
2. **能力即钥匙**：地图的门槛由移动能力决定，而不是由数值或钥匙道具决定。这让关卡和引擎的物理系统天然耦合。
3. **房间即谜题，死亡近乎免费**：死亡后 0.5 秒内回到当前房间入口，鼓励反复试错。
4. **小而完整**：宁可 6 种能力、5 个区域做透，也不要 15 种能力做成半成品。

**技术画像（决定后面所有引擎需求的前提）**

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 内部分辨率 | 320×180，整数倍缩放 | 像素完美，和蔚蓝一致 |
| 逻辑帧率 | 固定 60 Hz 时间步，渲染可高于 60 | 手感依赖确定性 |
| 视角 | 横版侧视，单屏房间 + 部分可滚动大房间 | 房间相机最简单 |
| 碰撞 | AABB + 瓦片（tile）网格，不依赖通用物理引擎 | 平台跳跃需要完全可控的“作弊式”物理 |
| 平台 | PC 优先（Windows/macOS/Linux），手柄 + 键鼠 | 先不做移动端 |
| 玩家数 | 单人 | 联机不在范围内 |

**明确不做**：联机、程序化地图、物品栏装备系统、复杂对话树、技能树、经济系统、可变分辨率 UI 适配之外的本地化。

## 2. 角色移动系统（蔚蓝式手感）

移动系统是整个项目的心脏，应当最先做、最后定稿。它是一个显式状态机，所有“手感”都来自状态之间的过渡细节，而不是单个参数。

**玩家状态机**

- **Normal**：地面/空中的常规移动与跳跃
- **Dash**：冲刺，含起手冻结帧、方向锁定、结束减速
- **Climb**：贴墙攀爬，消耗体力
- **WallSlide**：贴墙下滑（属于 Normal 的子状态，但独立处理速度上限）
- **Hurt / Dead**：受击硬直、死亡、重生
- **Cutscene / Locked**：剧情或过场中被脚本接管输入

**必须实现的手感细节**

| 机制 | 行为 | 为什么是硬需求 |
| --- | --- | --- |
| 土狼时间（coyote time） | 离开平台边缘后约 0.1 秒内仍可起跳 | 消除“明明按了却没跳”的挫败感 |
| 输入缓冲（jump buffer） | 落地前约 0.08 秒内按跳跃，落地瞬间自动起跳 | 让连续跳跃变得顺手 |
| 可变跳跃高度 | 按住跳跃键时重力减半一小段时间，松开则正常下落 | 跳跃高度由玩家控制 |
| 顶点半重力 | 跳跃顶点附近垂直速度很低时重力减半 | 制造“悬空”的滞空感 |
| 角落修正（corner correction） | 跳跃撞到天花板边角时，水平位移几像素让玩家“滑”过去 | 避免被头顶一像素卡住 |
| 地面/平台边缘修正 | 冲刺时贴近平台边缘自动抬升几像素 | 让冲刺不被“差一像素”挡住 |
| 冲刺方向 | 8 方向，斜向速度归一化；冲刺前有约 3 帧冻结 | 打击感，也给玩家反应时间 |
| 冲刺次数 | 空中 1 次，落地或碰到特定物体时恢复 | 关卡设计的基本单位 |
| 超级冲刺类技巧 | 地面冲刺后立即起跳可获得额外水平速度 | 可选的高阶技巧，决定是否保留需尽早定 |
| 蹬墙跳 | 贴墙时起跳，获得远离墙面的水平速度 | 与爬墙配合 |
| 墙面检测宽容 | 离墙 1–2 像素也能起跳/蹬墙 | 宽容度 |
| 体力系统 | 爬墙消耗体力，静止少耗，向上多耗，落地恢复 | 限制爬墙使用时长 |
| 抓取与携带 | 抓住并搬运物体（可后置） | 引入 Entity 间的父子关系需求 |

**起始参考参数**（量级参考，按 320×180、像素/秒为单位；来自社区对蔚蓝手感的公开分析，属于大致数值，需要你在自己的引擎里实测调校，不要当作精确值）

| 参数 | 参考值 |
| --- | --- |
| 水平最大跑速 | 约 90 px/s |
| 地面加速度 | 约 1000 px/s² |
| 空中加速度系数 | 地面的约 0.65 倍 |
| 重力 | 约 900 px/s² |
| 最大下落速度 | 约 160 px/s（按住下可加快至约 240） |
| 起跳速度 | 约 105 px/s |
| 可变跳跃保持时间 | 约 0.2 秒 |
| 土狼时间 / 输入缓冲 | 约 0.1 秒 / 约 0.08 秒 |
| 冲刺速度 / 持续时间 | 约 240 px/s / 约 0.15 秒 |
| 冲刺结束速度 | 约 160 px/s |
| 爬墙速度 | 约 45 px/s（上）/ 80 px/s（下） |
| 体力上限 | 约 110 单位 |

**工程要求**

1. 所有数值放进数据文件（不是硬编码），支持游戏运行时热重载，改完立即手感试玩。
2. 玩家移动用**固定时间步 + 整数/亚像素位置**，水平和垂直**分轴移动并逐像素检测碰撞**，这是确定性与手感的基础。
3. 提供“输入回放”：录一段输入序列，能稳定复现同一条轨迹，用于手感回归测试。
4. 物理调试叠加层：显示碰撞盒、速度向量、当前状态名、土狼/缓冲计时器。

## 3. 战斗与交互系统

《蔚蓝》本身没有战斗，银河恶魔城通常有。建议走“轻战斗”路线：战斗只是移动系统的延伸，而不是第二套玩法，这样工作量最可控。

**最小战斗集（建议）**

- **近战斩击**：一个短距离攻击判定盒，约 0.15 秒持续，可在空中使用，冷却很短。
- **冲刺攻击**：冲刺过程中碰到特定敌人可造成伤害或弹开（把移动能力变成战斗能力，不需要额外按键）。
- **受击与无敌帧**：被击中后短暂硬直 + 约 1 秒闪烁无敌；击退方向取决于来源。
- **生命值**：整数格子（如 5 格），可通过检查点或道具恢复；死亡即重生，无“游戏结束”画面。

**交互系统**

- 通用交互键：开门、对话、使用存档点、拉杆。
- 交互提示：靠近可交互物体时显示图标，离开后淡出。
- 玩家与实体的接触规则：伤害接触、推动、站立（载具/移动平台）、触发区（trigger volume）。

**实现上必须区分的三类碰撞盒**

| 类型 | 用途 | 例子 |
| --- | --- | --- |
| Hurtbox（受击盒） | 能被伤害的区域 | 玩家身体、敌人身体 |
| Hitbox（攻击盒） | 造成伤害的区域 | 斩击、敌人的爪子 |
| Solid / Trigger | 阻挡 / 触发事件 | 墙、弹簧、传送区 |

**可选扩展（有余力再做）**：远程投射物、格挡/弹反、可升级的攻击力。这些会显著增加敌人设计与平衡的工作量，不建议进首个里程碑。

## 4. 能力解锁与门控

5 种核心能力（外加 1 种可选）构成整张地图的“锁与钥匙”。每种能力都必须同时满足三点：改变移动规则、能被一眼看懂的门槛挡住、在后期能与其他能力组合。

| 顺序 | 能力 | 对移动系统的改动 | 典型门槛（被它解锁的东西） |
| --- | --- | --- | --- |
| 0 | 基础移动 | 跑、跳、可变跳跃、土狼、缓冲 | 起始区域 |
| 1 | 蹬墙跳 | 贴墙起跳，获得反向水平速度 | 过高的竖井、窄缝 |
| 2 | 空中冲刺 | 空中 1 次 8 向冲刺，落地恢复 | 宽沟、需要穿越的危险区 |
| 3 | 攀爬 | 抓墙、消耗体力 | 长垂直墙面、体力限制的路线 |
| 4 | 二段跳或浮空 | 空中再跳一次（或短暂缓降） | 需要精确落点的悬空平台 |
| 5 | 冲刺破障 | 冲刺可击碎特定脆弱物 | 被封死的捷径与隐藏房 |
| 6 | 水中/气流移动（可选） | 特殊介质中的运动规则 | 水下区域、气流井 |

**设计规则**

1. 每种能力获得后，**立刻**安排一个只能用它通过的房间（教学房），再安排 2–3 个需要组合使用的房间。
2. 一旦玩家拿到某能力，应当能看到至少一处自己此前见过、但当时过不去的地方，这是回溯的动机。
3. 避免“硬锁死”：任何时刻玩家都不应因能力不足而无法回到上一个存档点。
4. 能力开关通过\*\*游戏状态标志（flag）\*\*表示，引擎需要提供一个全局的、可存档的 flag 系统，关卡里的门、机关、NPC 台词都读取同一份 flag。

**数据层需求**：能力清单、解锁条件、对应的教学房间，建议用一份表格式数据（如 JSON/CSV）维护，而不是写进代码。这让关卡设计者可以在不改代码的情况下重排解锁顺序。

## 5. 世界与地图结构

世界是 5 个区域沿一口竖井向下排列的链状结构，每个出口都由上一区域给出的能力打开。

&#91;embedded content: 世界拓扑 · 5 个区域，4 道能力门槛\]

玩家每深入一层，就带着新能力回头打开此前见过却过不去的地方；最后一道门槛要求同时使用两种能力。

**房间系统**

- 一个房间 = 一张瓦片地图 + 实体列表 + 相机边界 + 出口连接。单屏房间为 320×180，大房间取其整数倍。
- 房间之间通过**出口**（门或屏幕边缘触发区）连接，出口记录目标房间与落点，玩家速度在切换时保留。
- 总量约 60–100 个房间，每个区域 12–20 个；每个区域有独立的瓦片集、背景、音乐与环境声。
- 每个房间有唯一 ID，供存档、地图、脚本引用。

**地图与导航**

- 小地图由“已访问房间”集合绘制，房间在地图上的位置来自编辑器里的网格坐标。
- 地图碎片道具解锁整个区域的轮廓，未访问的房间显示为暗色。
- 存档点之间可快速传送，前提是双方都已激活；传送是一次“加载房间 + 转场”，不应有额外的特殊路径。
- 每个区域至少有 1 条**回溯捷径**（单向门或电梯），避免玩家为了回头收集而重走长路。

## 6. 关卡机关与环境元素

每个机关都是一个独立的实体（Entity），带有自己的状态、碰撞与触发规则。这一节是引擎“实体/组件系统”和“碰撞系统”最直接的需求来源。

| 机关 | 行为 | 对引擎的要求 |
| --- | --- | --- |
| 尖刺 / 岩浆 | 接触即死或扣血，有方向性 | 带方向的伤害区域，死亡事件 |
| 移动平台 | 沿路径往返，玩家站上去会被带走 | **载具（riding）**：平台移动时带动其上的实体，需要处理挤压 |
| 单向平台 | 可从下方穿过，从上方站立 | 碰撞层的方向性判定，下穿操作 |
| 弹簧 / 弹跳蘑菇 | 踩上去获得固定弹射速度 | 速度覆盖、与跳跃状态的交互 |
| 冲刺恢复水晶 | 碰到后恢复冲刺次数，短暂消失后重生 | 实体显隐、计时器、与玩家状态通信 |
| 掉落平台 | 踩上后延迟掉落，一段时间后复原 | 状态机、计时器、实体重置 |
| 可破坏墙 | 冲刺或攻击后破碎 | 受击事件、瓦片/实体替换、存档记录“已破坏” |
| 开关 + 门 | 拉杆/压力板控制门开闭 | 全局 flag、实体间引用、动画 |
| 风/气流区 | 区域内持续施加力 | 触发区域内的持续效果 |
| 水体 | 改变重力与移动速度 | 区域内的物理参数切换 |
| 传送门/房间出口 | 切换到相邻房间并保持玩家速度 | 房间切换的数据与过渡 |
| 收集品 | 触碰后消失并记入存档 | 一次性实体的持久化 |

**共通要求**

1. 所有机关在**玩家死亡重生时重置**到房间初始状态（已被存档记录的永久变化除外，如已打开的门、已破坏的捷径）。
2. 机关的参数（速度、延迟、路径点）必须能在关卡编辑器里直接设置，不改代码。
3. 实体生命周期要明确：房间加载时创建、离开房间时销毁、重生时重置。这决定了“房间”在你引擎里是不是一等概念。

## 7. 敌人与 Boss

敌人数量宁少勿滥：6 种普通敌人 + 3 个 Boss 已经足够覆盖大多数引擎需求。每个敌人都应是“一种移动模式 + 一种威胁方式”的简单组合，并且能教会玩家一件事。

**普通敌人（建议 6 种）**

| 敌人 | 行为 | 主要考验的引擎能力 |
| --- | --- | --- |
| 巡逻者 | 在平台上往返，遇边缘/墙转向 | 地面检测、边缘检测 |
| 飞行游荡者 | 沿正弦或路径点飞行 | 路径/曲线移动 |
| 追踪者 | 进入感知范围后追向玩家 | 视线/距离感知、简单寻路 |
| 固定炮台 | 周期性发射投射物 | 投射物实体、对象池 |
| 跳跃者 | 蓄力后抛物线跳向玩家 | 与玩家同一套物理，状态机 |
| 护盾兵 | 正面免疫，需要绕后或冲刺破盾 | 方向性受击判定 |

**敌人 AI 的统一结构**：每个敌人是一个小状态机（Idle → Alert → Attack → Recover → Dead），状态切换由计时器和感知事件驱动。引擎需要提供：状态机工具、计时器、视线检测（射线或区域）、以及可复用的移动行为组件。

**Boss 战（建议 3 个）**

1. **区域守卫 Boss**（教学型）：1 个阶段，3 种攻击，模式固定、可预判，用来检验刚学会的能力。
2. **中段 Boss**：2 个阶段，血量过半后攻击模式变化，战场会出现机关。
3. **最终 Boss**：3 个阶段，要求使用全部移动能力，每个阶段结束有一段短过场。

**Boss 战的通用需求**

- **Boss 房间锁定**：进入后门关闭、相机锁定、Boss 血条显示，战斗结束后解锁。
- **阶段脚本**：用**协程或时间线脚本**描述攻击序列（等待 → 预警 → 攻击 → 恢复），比纯状态机更好写。
- **攻击预警**：每个攻击都有明确的视觉/音效预警，这是公平感的来源。
- **失败重试**：死亡后立即回到 Boss 房间入口，Boss 状态完全重置，不需要重新走一段路。

## 8. NPC、叙事与收集

叙事保持克制：用环境和少量对话讲故事，避免复杂分支。这一块的价值在于逼出引擎的**对话框、文本、脚本事件**三项基础能力。

**NPC 与对话**

- 8–12 个 NPC，全部是线性对话（最多根据 flag 切换几句不同台词）。
- 对话框：逐字显示、可跳过、支持换行与简单的富文本（颜色、停顿、抖动）。
- 对话期间玩家输入被接管，结束后归还。
- 说话人头像或名字标签，位置在屏幕下方或角色上方。

**过场与脚本事件**

- 简单的“事件脚本”：移动相机、让角色走到某点、播放动画、等待、显示对话、设置 flag。
- 用协程/时间线写成一串顺序步骤，而不是在游戏代码里硬写状态机。
- 过场中可被跳过（按住某键）。

**收集与进度**

| 类别 | 数量 | 作用 |
| --- | --- | --- |
| 能力道具 | 5（可选第 6 种） | 主线进度 |
| 生命上限碎片 | 约 10 | 4 个碎片换 1 格生命，鼓励探索 |
| 隐藏收集品 | 约 20 | 纯成就性质，对应完成度百分比 |
| 地图碎片 | 每区 1 | 解锁该区域的完整地图显示 |

**成就与统计**：记录死亡次数、游玩时间、收集完成度，在存档界面显示。成就系统本身可以后置，但统计数据建议从一开始就记录。

**本地化**：所有文本走字符串表（key → 文本），不要把字符串写进代码。即使首发只有一种语言，这条也值得从第一天做对，因为后补成本很高。

## 9. 存档、检查点与死亡重生

这套系统要区分两种完全不同的“记住”：**房间内的临时状态**（死亡就重置）和**世界的永久状态**（写入存档）。混淆它们是银河恶魔城最常见的 bug 来源。

**死亡与重生流程（目标：总耗时约 0.5 秒）**

1. 玩家死亡：冻结约 3–5 帧，播放短促的死亡特效。
2. 屏幕做快速转场（擦除或缩放）。
3. 房间内所有实体重置到初始状态，玩家出现在该房间的入口点（或最近的房内检查点）。
4. 立即恢复控制，不需要任何按键确认。

**存档点保存的内容**

| 数据 | 说明 |
| --- | --- |
| 世界 flag 表 | 门是否已开、Boss 是否已击败、能力是否已获得 |
| 已收集物集合 | 以稳定的实体 ID 记录，避免重复出现 |
| 玩家状态 | 当前生命上限、已解锁能力、所在房间与存档点 |
| 地图探索度 | 已访问房间集合，用于绘制地图 |
| 统计数据 | 死亡次数、游玩时间 |

**设计要点**

- 存档点是房间里的一个实体，玩家交互后恢复生命并写盘；检查点（自动、仅限本次游玩）可以更密集。
- 存档格式用带版本号的文本/二进制结构（如 JSON + version 字段），版本变化时提供迁移函数。这是引擎的“序列化”需求。
- 实体需要**稳定 ID**：在编辑器里放置时分配，运行时不变，存档才能指向“第 3 个房间的那个宝箱”。
- 支持 3 个存档槽、手动删除；写盘用“先写临时文件再原子重命名”，避免掉电损坏。
- 自动存档在进入新区域、击败 Boss、获得能力时触发。

## 10. 相机、画面、音频与特效

这一节决定“看起来和听起来像不像一个完整的游戏”，同时是渲染和音频模块的主要需求来源。

**相机**

- **房间相机**：每个房间有自己的边界，相机夹在边界内；房间切换时平滑过渡或硬切。
- **跟随与前瞻**：水平方向略微前瞻玩家朝向，垂直方向在落地/起跳时平滑，避免来回抖动。
- **相机区域**：房间内可划分多个相机区（不同边界或固定镜头），用于 Boss 房和大型房间。
- **屏幕震动**：强度、持续时间、衰减可调，带“减少震动”的无障碍开关。

**渲染**

| 需求 | 说明 |
| --- | --- |
| 瓦片地图渲染 | 多层（背景、碰撞层、前景），按相机裁剪，批量绘制 |
| 精灵与动画 | 精灵图集、帧动画、事件帧（如脚步声触发帧）、翻转 |
| 视差背景 | 多层背景以不同速度滚动 |
| 像素完美输出 | 先渲染到固定分辨率的离屏缓冲，再整数倍放大 |
| 粒子系统 | 冲刺残影、落地灰尘、受击火花，需要对象池 |
| 光照/后处理（可选） | 简单的屏幕闪白、色调变化、暗角；复杂光照放后期 |
| 帧冻结（hitstop） | 冲刺起手、受击时全局暂停几帧，是手感关键 |

**音频**

- 音效：同时播放多路、音量/音调随机化、位置衰减（可选）。
- 音乐：循环播放、区域切换时淡入淡出，支持**分层音乐**（同一首曲子随进度加入更多声部）。
- 总线与音量设置：音乐、音效、环境声三条总线，各自可调。
- 事件驱动：所有音效由游戏事件触发（“跳跃”“冲刺”“落地”），不在逻辑代码里直接调用文件名。

**镜头语言上的细节**：冲刺时的残影与轻微屏幕缩放、落地时的灰尘、死亡时的爆散粒子，这些都应该在第一个里程碑就有粗糙版本，因为它们会直接影响你对手感的判断。

## 11. UI 与菜单

UI 系统不需要做成通用 GUI 框架，只要能支撑下面这些具体界面，并且手柄操作完全可用。

| 界面 | 内容 | 关键需求 |
| --- | --- | --- |
| HUD | 生命格、当前区域名（进入时淡入淡出）、收集提示 | 屏幕空间绘制，不受相机影响 |
| 主菜单 | 开始、继续、设置、退出，存档槽选择 | 焦点导航（上下左右 + 确认/返回） |
| 暂停菜单 | 继续、地图、设置、返回主菜单 | 暂停时游戏逻辑冻结但 UI 仍运行 |
| 地图界面 | 已探索房间、当前位置、存档点标记、区域着色 | 由“已访问房间”数据动态绘制，可缩放/滚动 |
| 设置 | 音量、画面（窗口/全屏/缩放）、输入重绑定、无障碍 | 即时生效、写入配置文件 |
| 对话框 | 逐字文本、选项（少量） | 与脚本系统联动 |
| 道具/能力获得弹窗 | 一次性展示新能力与操作提示 | 过场式、可跳过 |
| 结算/统计 | 通关后显示时间、死亡次数、收集率 | 读取统计数据 |

**技术要点**

1. UI 与游戏世界分层渲染：世界 → 特效 → HUD → 菜单 → 转场遮罩。
2. 菜单用**焦点图**导航，而不是鼠标点击为主；鼠标支持可作为附加。
3. 文本渲染要支持像素字体、自动换行、多语言字符集（至少覆盖中英文）。
4. 转场（淡入淡出、擦除）是独立的全屏效果层，可被房间切换、死亡、过场复用。

**辅助模式（参考蔚蓝的做法）**：游戏速度调节、无限冲刺、无敌、跳过 Boss 战等选项，放在设置里，对引擎的要求是“关键参数可在运行时被覆盖”。

## 12. 输入与可访问性

平台跳跃对输入延迟极其敏感，输入层要做得薄而稳定，并且从第一天就把“动作”与“物理按键”分离。

**输入抽象**

- 游戏逻辑只读取**动作**（跳跃、冲刺、攻击、抓取、交互、暂停），不直接读按键。
- 每个动作可绑定多个物理输入（键盘按键、手柄按钮、摇杆方向）。
- 方向输入统一成一个向量，带**死区**处理和 8 方向量化（冲刺用）。
- 每个动作提供三种状态查询：按下的那一帧、按住中、松开的那一帧。
- 输入在**固定逻辑步**上采样，保证同一输入序列产生同一结果（支撑回放与测试）。

**设备支持**

| 项 | 要求 |
| --- | --- |
| 键盘 | 默认 + 完全可重绑定 |
| 手柄 | 主流手柄即插即用，摇杆死区可调，按钮可重绑定 |
| 热插拔 | 运行中插拔手柄不崩溃，自动切换提示图标 |
| 按键提示 | 对话/教程里的按键图标随当前输入设备变化 |

**可访问性清单**

1. 全部按键可重绑定；“按住”类操作（抓墙）提供“切换”模式。
2. 辅助模式：调整游戏速度、无限冲刺、无敌等（见第 11 节）。
3. 减少屏幕震动、闪光的选项。
4. 字幕与对话文字大小可调；不单靠颜色传递信息。
5. 音频三条总线独立调节。

## 13. 内容管线与工具

这个项目的内容量（几十到一百多个房间）决定了：**没有顺手的工具，内容就做不出来**。工具链本身就是引擎需求的一大来源，也最能暴露引擎数据格式设计的问题。

**关卡编辑**

- 可以用现成编辑器（如 Tiled / LDtk）导出，再由你的引擎导入；也可以自己做。**建议先用现成的**，把精力留给引擎本体。
- 编辑器至少要表达：多层瓦片、实体放置（带参数）、触发区域、房间边界、房间之间的连接点。
- 房间数据格式要稳定、可版本化、可文本 diff（JSON 之类），便于协作与回滚。
- 引擎支持**运行时热重载**：保存关卡文件后，游戏中的当前房间立即刷新。

**资源管线**

| 资源 | 处理 |
| --- | --- |
| 图片 | 自动打成图集，保留原始文件供美术修改 |
| 动画 | 从导出的帧数据（如 Aseprite 的 JSON）读取 |
| 音频 | 压缩格式，音乐流式加载、音效整段载入 |
| 字体 | 位图字体或 TTF 预渲染 |
| 配置/数值 | 文本文件，支持热重载 |

**调试与开发者工具（强烈建议，都很便宜）**

1. 调试叠加层：碰撞盒、实体 ID、状态名、帧时间。
2. 控制台/命令：传送到指定房间、设置 flag、解锁全部能力、切换无敌。
3. 时间控制：暂停、单步前进一帧、慢放。
4. 输入录制与回放（见第 2 节）。
5. 性能面板：每帧耗时、实体数量、绘制调用数。
6. 日志系统：分级、可按模块过滤。

## 14. 引擎需求映射表

下表把游戏功能翻译成引擎模块，并给出可检验的验收标准。你可以把它当作引擎的待办清单：每一行做完，就用对应的游戏功能去验证它。

| 引擎模块 | 由哪些游戏功能驱动 | 验收标准 |
| --- | --- | --- |
| 主循环与固定时间步 | 手感、回放 | 逻辑固定 60 Hz，渲染帧率变化不影响跳跃高度 |
| 输入系统 | 所有操作、重绑定 | 同一输入序列回放，轨迹逐帧一致 |
| 瓦片碰撞 | 跑、跳、爬墙、角落修正 | 玩家不会卡进墙、不会在平坦地面上抖动 |
| 实体/组件系统 | 机关、敌人、玩家、收集品 | 新增一种机关只需写一个类/组件和一份数据 |
| 实体间通信（事件） | 水晶恢复冲刺、开关开门 | 不直接引用对方也能完成交互 |
| 状态机工具 | 玩家、敌人、Boss | 状态切换有进入/退出回调，可打印当前状态 |
| 协程/时间线脚本 | Boss 阶段、过场、对话 | 一段 20 行脚本能表达“走到 A → 说话 → 开门” |
| 房间系统 | 房间切换、重置、相机边界 | 切换房间无闪烁，死亡后房间完全重置 |
| 渲染（瓦片/精灵/图集） | 全部画面 | 在目标机器上稳定 60 FPS，像素无缝隙 |
| 动画系统 | 角色、敌人、特效 | 动画事件帧可触发音效/判定 |
| 粒子系统 | 冲刺、灰尘、受击 | 数千粒子无明显掉帧，使用对象池 |
| 相机 | 房间相机、震动、锁定 | 切房间与 Boss 锁定无跳变 |
| 音频 | 音效、分层音乐 | 同时 16 路以上音效，音乐切换无爆音 |
| UI/文本 | 菜单、对话、地图 | 手柄可完整操作所有菜单，中文正常显示 |
| 序列化/存档 | 存档、flag、收集品 | 存档读回后世界与退出前一致，旧版本存档能迁移 |
| 资源管理 | 关卡、图集、音频加载 | 切房间不卡顿，资源不泄漏 |
| 热重载 | 数值、关卡、脚本调试 | 保存文件后 1 秒内在游戏里生效 |
| 调试工具 | 开发效率 | 可在游戏内传送、设置 flag、单步执行 |
| 打包与发布 | 交付 | 一条命令产出可在干净机器上运行的版本 |

**使用方法**：不要按模块逐个“做完”再做游戏。按下一节的里程碑，每次只推进游戏需要的那一小块引擎能力，用游戏验证，再回头抽象。

## 15. 里程碑与垂直切片

开发分 5 个阶段，每个阶段结束都有一道必须通过的关卡，没过就不进入下一阶段。

时间没有写进图里：它取决于你每周能投入多少，建议用 M0 的实际用时去校准后面几个阶段。

**执行原则**

1. **M2 垂直切片是最重要的节点**：它第一次让几乎所有引擎模块同时工作，暴露的问题最多。
2. 每个阶段只做该阶段游戏需要的引擎能力，用游戏验证后再回头抽象。
3. 灰盒优先：手感和关卡定稿前不批量制作美术，M2 之后再换成正式资源。
4. 每个阶段结束时，留一个可运行的版本（打 tag），便于回退与对比手感。

## 16. 范围控制与风险

这个项目最大的风险不是做不出某个功能，而是**一直在做引擎、一直没有可玩的游戏**。下面是最容易失控的几项，以及建议的处理方式。

| 风险 | 为什么会失控 | 建议处理 |
| --- | --- | --- |
| 手感反复调不好 | 参数互相牵连，没有回放就无法比较 | 先做输入回放和热重载，再调数值 |
| 房间切换与重置的 bug | 临时状态与永久状态混淆 | 第 9 节的两类状态严格分开，先写测试房间 |
| 关卡内容拖垮进度 | 房间数量多，工具不顺手 | 先做 15 个房间的垂直切片，再扩量 |
| 地图界面和探索度 | 看似简单，实则牵涉存档与 UI | 放到里程碑 4 之后 |
| Boss 战调平衡 | 阶段脚本、预警、重试都要打磨 | 首版只做 1 个 Boss，其余后置 |
| 过早通用化 | 为“将来的游戏”设计抽象 | 只抽象这个项目已经用到两次以上的东西 |
| 美术资源缺口 | 动画和瓦片量大 | 先用灰盒占位，手感和关卡定了再上美术 |

**建议砍掉或推迟的内容**

- 水下/气流等特殊介质（能力 6）
- 抓取并搬运物体
- 分层音乐的复杂版本（先做简单切换）
- 成就系统（只保留统计）
- 光照与复杂后处理
- 鼠标菜单支持

**判断一个功能该不该做的三个问题**

1. 它是否推动了某个引擎模块第一次被真正使用？
2. 没有它，垂直切片还能玩吗？
3. 它能在一个周末内做到可验证吗？

三个答案里有两个是“否”，就先放进待办池。
